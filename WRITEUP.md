# Design write-up — BookLeaf Author Support Portal

**Approach.** I treated this as an operations product, not a chat demo. The core problem is context: an author should not have to repeat their book, royalty balance or production stage, and an admin should not have to hunt across systems before replying. The portal therefore centres on one contextual ticket workspace for admins and one clear account view for authors. AI removes blank-page latency and routes work; it never sends a response on its own.

**What I prioritised.**

- **The full ticket loop first.** Login, author-scoped data, create → triage → draft → reply → resolve, internal notes, overrides and realtime updates all work end to end. Fancier extras came after that path was solid.
- **Context in the prompt and on screen.** The admin sees the linked book, MRP, copies sold, royalties earned/paid/pending, last payout, print partner and channels next to the conversation. The AI sees the same facts plus one policy slice.
- **Trust boundaries.** Authors only ever receive their own tickets, never internal notes and never `ai_draft_response`. Redaction happens in the server serializer, not in React, and SSE payloads carry metadata only.
- **Graceful failure.** If AI times out, is rate-limited or returns invalid JSON, ticket creation still succeeds with `General Inquiry` / `Medium`, `ai_classified=false` and no draft. The admin sees a manual-triage state and can regenerate or reply manually.

**Architecture.** FastAPI routes stay thin; services own ticket invariants, AI orchestration and event broadcasting; SQLAlchemy models and Pydantic v2 schemas are separate contracts. A custom UTC datetime type keeps SQLite and Postgres behaviour consistent. Alembic reads `DATABASE_URL` from application settings, so the same migrations work locally and in deployment. The React/Vite/TypeScript frontend uses TanStack Query for cache ownership, React Router guards for role separation, and a small design system (paper/forest/gold) for a publishing-house feel. SSE invalidates query caches; polling remains the fallback.

**AI integration.** A provider factory resolves OpenAI, Anthropic, Groq/Together and local Ollama/vLLM from environment variables; all but Anthropic share the OpenAI-compatible protocol, so switching models requires no code change. Outputs must satisfy a strict `AITriageResult` schema, with markdown fences and trailing commas stripped and enum aliases normalised. Calls have an 8-second timeout, one retry, an overall budget and optional dual-engine fallback.

Cost control comes from **modular context, not a giant prompt**. The service sends the author snapshot, the linked book, the public ticket and only the relevant category KB slice (~250 tokens) plus tone rules. Regeneration re-sends only the overridden category. This keeps 3B–8B SLMs accurate and makes them the economical choice for routine categories, with frontier models reserved for ambiguous or high-stakes cases. `AI_PROVIDER=mock` runs a deterministic rule engine by default, so the demo works offline and production has a safe last-resort path. Drafts are editable and admin-sent only, which is the quality gate for smaller models.

**Trade-offs.** The SSE broker is in-process, which is correct for one instance but needs Redis pub/sub to scale horizontally. AI runs synchronously on ticket creation, trading submit latency for an immediately available draft; a job queue is the next step at higher volume. Attachments store the filename only, as the brief allows. There is no outbound email, rate limiting or audit trail yet; those belong in a hardening pass. The rules engine is keyword-based and predictable, but not semantic — real provider quality should be measured on a labelled evaluation set before any auto-send.

**Production evolution.** I would add a worker queue for AI and notifications, Redis-backed SSE, object storage for attachments, an audit log for overrides and internal notes, rate limiting at the edge, and a provider evaluation harness reporting precision/recall per category with a human-review gate. The current Docker images, health checks, migrations, idempotent seed and 41-test suite are intended as the base for that evolution rather than a throwaway prototype.
